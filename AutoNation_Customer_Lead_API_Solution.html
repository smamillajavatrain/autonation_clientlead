1. Solution Overview

The solution separates customer-facing lead capture from CRM lifecycle management. Spring Boot exposes REST APIs, the service layer contains business rules, Spring Data JPA/Hibernate handles persistence, and MySQL stores lead, assignment and lifecycle information.

MySQL – customer_lead

CREATE TABLE customer_lead (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(150) NOT NULL,
    email VARCHAR(150) NOT NULL,
    phone VARCHAR(20),
    comment TEXT,

    account_manager_id BIGINT,

    status VARCHAR(30) NOT NULL,
    close_reason VARCHAR(30),

    idempotency_key VARCHAR(100),

    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP,

    CONSTRAINT fk_lead_manager
        FOREIGN KEY (account_manager_id)
        REFERENCES account_manager(id),

    INDEX idx_lead_name (name),
    INDEX idx_lead_email (email),
    INDEX idx_lead_phone (phone),
    INDEX idx_lead_status (status),
    INDEX idx_lead_manager (account_manager_id),

    UNIQUE KEY uk_lead_idempotency (idempotency_key)
);

JPA Entity

@Entity
@Table(name = "customer_lead")
public class CustomerLead {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 150)
    private String name;

    @Column(nullable = false, length = 150)
    private String email;

    @Column(length = 20)
    private String phone;

    @Column(columnDefinition = "TEXT")
    private String comment;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "account_manager_id")
    private AccountManager accountManager;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 30)
    private LeadStatus status;

    @Enumerated(EnumType.STRING)
    @Column(length = 30)
    private CloseReason closeReason;

    @Column(name = "idempotency_key", unique = true, length = 100)
    private String idempotencyKey;

    private LocalDateTime createdAt;
    private LocalDateTime updatedAt;

    @Version
    private Long version;
}

4. Question 3 – Prevent Duplicate Customer Leads

Requirement

The system must prevent duplicate records when customers submit the same lead multiple times. The solution distinguishes between a repeated HTTP request and a business-level duplicate customer lead.

Duplicate Detection

The service layer performs a duplicate check through the repository using normalized customer data, for example email and phone. The exact matching rule should be agreed with the business because the same customer may legitimately create more than one lead over time. 

public interface CustomerLeadRepository
        extends JpaRepository<CustomerLead, Long> {

    Optional<CustomerLead>
        findFirstByEmailIgnoreCaseAndPhone(
            String email,
            String phone);

    Optional<CustomerLead>
        findByIdempotencyKey(String idempotencyKey);
}

Service Logic

@Transactional
public CustomerLeadResponse createLead(
        CustomerLeadRequest request,
        String idempotencyKey) {

    if (idempotencyKey != null) {
        Optional<CustomerLead> existing =
            repository.findByIdempotencyKey(idempotencyKey);

        if (existing.isPresent()) {
            return mapper.toResponse(existing.get());
        }
    }

    String email = request.getEmail()
            .trim()
            .toLowerCase();

    String phone = normalizePhone(request.getPhone());

    Optional<CustomerLead> duplicate =
        repository.findFirstByEmailIgnoreCaseAndPhone(
            email, phone);

    if (duplicate.isPresent()) {
        return mapper.toResponse(duplicate.get());
    }

    CustomerLead lead = mapper.toEntity(request);
    lead.setEmail(email);
    lead.setPhone(phone);
    lead.setIdempotencyKey(idempotencyKey);
    lead.setStatus(LeadStatus.NEW);

    return mapper.toResponse(repository.save(lead));
}
Concurrency: A service-level SELECT followed by INSERT should not be treated as the only protection. Two concurrent requests can both pass the SELECT. A database UNIQUE constraint is appropriate for any business invariant that must never be violated.

Idempotency-Key

For repeated submission of the same HTTP request, the client can send an Idempotency-Key. The key identifies one logical submission. A repeated request with the same key returns the previously created lead instead of creating another lead. 

POST /api/leads
Idempotency-Key: 8f7a9c12-1234-4567

{
  "name": "Srikanth Mamillapalli",
  "email": "smamilla1208@outlook.com",
  "phone": "9739211566",
  "comment": "Interested in a vehicle"
}

MySQL supports this design because idempotency_key is a normal VARCHAR column and can have a UNIQUE index. 

ALTER TABLE customer_lead
ADD CONSTRAINT uk_customer_lead_idempotency
UNIQUE (idempotency_key);

Recommended Duplicate Strategy

ScenarioSolution
Same HTTP request submitted repeatedlyIdempotency-Key
Same customer submits an existing leadService + Repository duplicate check
Concurrent requestsDatabase UNIQUE constraint for applicable uniqueness rules
Legitimate future lead from the same customerDo not make email/phone globally unique unless the business requires it

SQL Concept

SELECT
    l.id,
    l.name,
    l.phone,
    l.email,
    am.id AS account_manager_id,
    am.name AS account_manager,
    l.status
FROM customer_lead l
LEFT JOIN account_manager am
    ON l.account_manager_id = am.id
WHERE
    (:name IS NULL OR
        LOWER(l.name) LIKE LOWER(CONCAT('%', :name, '%')))
AND (:email IS NULL OR
        LOWER(l.email) LIKE LOWER(CONCAT('%', :email, '%')))
AND (:phone IS NULL OR
        l.phone LIKE CONCAT('%', :phone, '%'))
AND (:accountManagerId IS NULL OR
        l.account_manager_id = :accountManagerId)
AND (:status IS NULL OR
        l.status = :status);

Implementation

Spring Data JPA Specification / Criteria API is suitable for this report because every filter is optional and the filters can be combined dynamically. Pagination should be implemented using Spring Data's Pageable.

8. Design Considerations

Transaction Management

Lead updates and their corresponding history records should be part of the same transaction. For example, changing a lead's status and creating its status-history row should either both succeed or both roll back. 

@Transactional
public CustomerLeadResponse moveToProposal(Long leadId) {

    // validate current state
    // update lead status
    // save lead
    // save status history

    // all operations participate in one transaction
}

Optimistic Locking

CRM users may update the same lead at the same time. The JPA @Version field helps detect lost-update scenarios and allows the application to return a conflict when an outdated record is saved.

Validation

public class CustomerLeadRequest {

    @NotBlank
    private String name;

    @NotBlank
    @Email
    private String email;

    @Pattern(regexp = "^[0-9+ -]{7,20}$")
    private String phone;

    private String comment;
}

Exception Handling

Use @RestControllerAdvice for consistent API error responses. Typical cases include invalid input, lead not found, account manager not found, invalid lifecycle transition, and duplicate constraint conflicts.

Security

  • Customer lead creation should have request validation and appropriate rate limiting.
  • CRM APIs should require authentication and authorization.
  • Assignment/reassignment should be restricted to authorized sales roles.
  • Lead status operations should follow role-based permissions.
  • Audit fields such as changed_by and assigned_by should come from the authenticated user context.

Auditability

The status and assignment history tables provide a record of the lead lifecycle and ownership changes. This supports traceability, reporting and operational troubleshooting.

10. Solution Summary

  • Lead Capture: REST API + DTO validation + JPA/Hibernate persistence.
  • CRM Lifecycle: Controlled status transitions with status and assignment history.
  • Duplicate Prevention: Repository/service business checks plus database uniqueness where required; Idempotency-Key for repeated HTTP submissions.
  • Reporting: Dedicated report DTO, dynamic filtering and pagination using Spring Data JPA.
  • Data Integrity: Foreign keys, unique constraints, transactions and optimistic locking.
  • Security: Authentication, authorization and audit information from the authenticated user.
